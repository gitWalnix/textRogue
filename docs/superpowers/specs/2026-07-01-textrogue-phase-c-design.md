# TextRogue — Phase C Design Spec

## Overview

Phase C fills in `Game.gameTick()` (empty since Phase B) with enemies, player HP, and ranged combat. The player gains a facing direction and a health bar; enemies chase the player and deal contact damage; the player fights back with a short-range projectile fired from a facing-relative position. No new abstraction layers are introduced — `Enemy` and `Projectile` are plain concrete classes alongside the existing `Player`, matching the codebase's existing style.

Combat is ranged-only: enemies block player movement (like a wall) but bumping into one does no damage. All player damage output comes from projectiles.

## What Changes

| File | Change |
|------|--------|
| `entity/Player.java` | Adds `hp`, `maxHp`, and a `Facing` field; facing updates on every move attempt (even blocked ones) |
| `entity/Facing.java` | New enum: `UP`, `DOWN`, `LEFT`, `RIGHT` |
| `entity/Enemy.java` | New: `x`, `y`, `hp`, alive state; one chase-step method |
| `entity/Projectile.java` | New: `x`, `y`, direction, remaining range; one advance method |
| `input/Command.java` | Adds `SHOOT` |
| `input/LanternaInputHandler.java` | Maps space bar to `SHOOT` |
| `Game.java` | `gameTick()` drives enemy AI and projectile movement; `processCommand` handles `SHOOT` (cooldown-gated) and updates facing on move; enemies spawned per floor; player death ends the loop |
| `render/LanternaRenderer.java` | Draws facing-dependent player glyph, enemies, projectiles, HP text, and a death screen |

`Dungeon`, `Tile`, `Room`, `DungeonGenerator` are untouched — enemies are placed by `Game`, not generated by `DungeonGenerator`.

## Balance Numbers

| Value | Amount |
|-------|--------|
| Player max HP | 20 |
| Enemy HP | 4 |
| Projectile damage | 2 |
| Enemy contact damage | 2 |
| Projectile range | 5 tiles |
| Projectile speed | 1 tile/tick |
| Shot cooldown | 5 ticks (1s) |
| Enemy chase radius | 6 tiles (Chebyshev distance) |
| Enemies per floor | random 3–5, one per randomly chosen non-start room |

These are starting values, expected to be retuned by playtesting rather than treated as final.

## Components

### Facing

```java
package ca.ninja.thenix.textrogue.entity;

public enum Facing {
    UP, DOWN, LEFT, RIGHT;

    public int dx() { return this == LEFT ? -1 : this == RIGHT ? 1 : 0; }
    public int dy() { return this == UP ? -1 : this == DOWN ? 1 : 0; }

    public char toChar() {
        return switch (this) {
            case UP -> '^';
            case DOWN -> 'v';
            case LEFT -> '<';
            case RIGHT -> '>';
        };
    }
}
```

### Player (additions)

- `hp` (default 20), `maxHp` (20), `facing` (default `Facing.DOWN`)
- `takeDamage(int amount)`: clamps `hp` to a minimum of 0
- `isDead()`: `hp <= 0`
- `setFacing(Facing)`: called by `Game` on every move attempt, regardless of whether the move succeeds

### Enemy

```java
package ca.ninja.thenix.textrogue.entity;

public class Enemy {
    private int x, y;
    private int hp;
    private boolean alive;
    // getters, takeDamage(int), isAlive()
}
```

No AI logic lives inside `Enemy` itself — chase-step decision-making is a pure method on `Game` (or a small package-private helper) so it can be unit tested against a `Dungeon` + player position without needing a full `Game` instance.

### Projectile

```java
package ca.ninja.thenix.textrogue.entity;

public class Projectile {
    private int x, y;
    private final Facing direction;
    private int remainingRange;
    // advance(): x/y += direction.dx()/dy(), remainingRange--
}
```

### Command

Adds `SHOOT`. `LanternaInputHandler` maps the space bar (`KeyType.Character` with `' '`, i.e. `key.getCharacter() == ' '`) to it. The existing drain-the-queue polling logic from the movement-lag fix applies unchanged — `SHOOT` is just another command value that can win the "latest command wins" resolution per tick.

## Game Loop

```
initialize dungeon, player, enemies (3-5, one per random non-start room)
render initial state
loop:
    record tick start time
    cmd = input.pollCommand()
    processCommand(cmd)
    gameTick()
    renderer.render(dungeon, player, enemies, projectiles)
    if player.isDead(): render death screen, break
    sleep(TICK_MS - elapsed)
```

### processCommand

- `MOVE_*`: set `player.facing` to the corresponding direction, then attempt the move as today. The move is blocked (no-op) if the target tile is a `WALL` **or** occupied by a living `Enemy`.
- `SHOOT`: if the cooldown counter is 0, spawn a `Projectile` at `(player.x + facing.dx(), player.y + facing.dy())` with `remainingRange = 5`, reset cooldown to 5 ticks. If that spawn tile is a `WALL`, the projectile is still created and consumes the cooldown, but is discarded immediately in the same tick's projectile-processing step (no special-case branch — it just fails its first wall check like any other tick). Pressing `SHOOT` while on cooldown is a no-op.
- `QUIT`: unchanged.

### gameTick()

1. **Cooldown**: decrement the shot cooldown counter (floored at 0).
2. **Enemy AI**: for each alive enemy within 6 tiles (Chebyshev) of the player, compute one step toward the player (axis-priority: reduce the larger of `|dx|`/`|dy|` first, matching the existing simple/no-pathfinding approach). Before moving, check the target tile:
   - If it's the player's tile: don't move, deal 2 contact damage to the player instead.
   - If it's a `WALL`: don't move (stays put this tick).
   - If it's already claimed by another enemy moving this tick: don't move (processed enemies in a fixed order; first-claimed wins, no swapping/stacking).
   - Otherwise: move onto it.
3. **Projectiles**: for each active projectile, check its *current* tile first, then advance — in that order, so a projectile's own spawn tile is validated the same tick it's created (it is never advanced-then-checked, which would skip validating the spawn position):
   - Current tile is `WALL` → remove the projectile, done (no advance).
   - Current tile has a living enemy → deal 2 damage to it, remove the projectile, done (no advance); if the enemy's HP drops to 0, mark it dead (removed from rendering/collision, no drops — items are Phase D).
   - Otherwise (clear tile) and `remainingRange > 0` → advance one tile, decrement `remainingRange`.
   - Otherwise (clear tile) and `remainingRange == 0` → remove the projectile (reached max range with nothing hit at the final tile; it doesn't advance past its range).

### Floor transitions

`descend()` (existing) regenerates the dungeon. Phase C adds: clear the enemy list and any in-flight projectiles, then spawn a fresh random 3-5 enemies in the new dungeon's non-start rooms. The shot cooldown is **not** reset on descend (no free shot from timing a stairway descent).

### Player death

Checked once per tick after `gameTick()` and rendering. When `player.isDead()`, the renderer draws a centered "You died" message (overwriting the normal frame), and the loop exits without the usual sleep. `Main` returns normally after `game.start()` completes — no explicit `System.exit` needed, matching how `QUIT` already ends the loop.

## Rendering

- Player glyph: `facing.toChar()` (`^`/`v`/`<`/`>`) in bright green (unchanged color).
- Enemies: `'e'` in red, drawn after the tile layer but before the player (player always draws on top if somehow overlapping, though normal collision rules should prevent that).
- Projectiles: `'*'` in yellow, drawn after enemies.
- HP: appended to the existing status line, e.g. `Floor: 2   HP: 14/20`.
- Death screen: `screen.clear()`, then `"You died"` centered on the map area, one `refresh()`, no further rendering.

## Testing

Following the existing JUnit 5 conventions from Phases A/B (plain `@Test` methods, no mocking framework):

- **PlayerTest additions**: `takeDamage` clamps at 0, `isDead` reflects HP, `setFacing` is reflected in `getFacing`.
- **EnemyTest**: construction, `takeDamage` reduces HP and flips `alive` at 0.
- **ProjectileTest**: `advance()` moves by direction and decrements range.
- **Chase-step logic test** (wherever it lives — likely a small testable method on `Game` or a standalone helper class): given a dungeon, enemy position, and player position, produces the expected single-step move, respects the 6-tile radius cutoff, and respects wall blocking.
- **GameTest additions**:
  - Enemy adjacent to player deals contact damage and does not move onto the player's tile.
  - `SHOOT` command spawns a projectile that, over subsequent ticks, damages an enemy in its path.
  - `SHOOT` on cooldown is a no-op (no new projectile).
  - Player reaching 0 HP stops the loop.
  - Descending floors clears old enemies/projectiles and spawns a new set.

## Out of Scope for Phase C

- Pathfinding (enemies use simple axis-priority chase, not A*/BFS)
- Multiple enemy types or varied stats
- Items, pickups, or enemy drops (Phase D)
- Fog of war (Phase D)
- Permadeath/restart flow beyond exiting on death (Phase D)
- Diagonal projectile or movement directions
- Enemy ranged attacks (contact damage only)
